# Contributing to Groundwork

Keep the workflow useful in both Codex and Claude Code. Changes should help
the agent find repository facts, ask material decisions through native forms,
and carry the answers into verified work.

## Local checks

Use Node.js 22.17.0 or newer:

```sh
npm ci
npm run check
npm test
```

These checks make no model calls. `npm test` runs the package, native-input,
workflow, and evaluation-harness tests.

If a Codex CLI is installed, run these additional checks:

```sh
npm run smoke
npm run native:doctor
```

The smoke check opens an app-server connection without starting a model turn.
The doctor checks native Default-mode input support and configuration.
`npm run validate` runs the type check, tests, and smoke check together.

## Package layout

```text
.claude-plugin/marketplace.json          Claude Code catalog, pointing at plugin/
.agents/plugins/marketplace.json         Codex catalog, pointing at plugin/
plugin/.claude-plugin/plugin.json        Claude Code plugin manifest
plugin/.codex-plugin/plugin.json         Codex plugin manifest and display metadata
plugin/skills/settle/SKILL.md            The skill, loaded by both hosts
plugin/skills/settle/agents/openai.yaml  Codex skill metadata
scripts/                                 Doctor, probe, and section helpers
test/                                    Package and behavior checks
eval/                                    Optional local evaluation harness
docs/                                    Installation, usage, and demo assets
```

The `plugin/` folder is the plugin for both hosts, so there is no generated
package and no build step, and hosts copy only that folder when they install.
Edit `plugin/skills/settle/SKILL.md` for behavior. Its
`## Native question tool` section is the only place that names a host's
question tool; it covers Claude Code and Codex side by side, and tests reject
host tool names anywhere else in the skill. The eval harness swaps that
section for a text adapter to build its text baseline.

## Verify behavior changes

For changed decision logic, try the updated package in a new session on each
host. Check a request with a real decision, a bare invocation, a custom
answer, a dependent follow-up, and the final native scope confirmation. Verify
that unanswered forms do not become assumptions and that confirmation
precedes implementation. Check Plan mode separately for no file changes.

The [evaluation harness](eval/README.md) provides repeatable fixtures and
optional model-driven runs. Live evaluations and `npm run native:probe`
consume your configured model usage; they are separate from the offline tests.
Keep generated runs and machine-specific configuration out of commits.

## Preparing a release

Keep the version in `package.json`, `package-lock.json`,
`plugin/.claude-plugin/plugin.json`, `plugin/.codex-plugin/plugin.json`,
and `.claude-plugin/marketplace.json` consistent, and update the expected
version in the package contract test when changing the release version.

Run the local checks and confirm the install and update commands against the
supported host CLIs. CI runs the same checks on Linux and Windows.

Record the release in `CHANGELOG.md`: move the entries under `Unreleased` to a
new version heading with the date, and add the comparison link at the bottom.
Then tag the release commit as `vX.Y.Z`, push the tag, and publish a GitHub
Release from it with the changelog entry as its notes. Plugin directories and
the release feed read tags, not the version fields in the manifests.

Use English for repository documentation and examples. Keep the public
README focused on installation and actual usage.

## Demo assets

The README uses `docs/assets/groundwork-seatwise-demo.gif`, edited from actual
screenshots of a Codex session. It shows repository discovery, native decision
questions, and the final scope check.

The illustrated export example in `docs/usage.md` uses `native-questions.gif`
and `native-questions.png`. These are generated by `scripts/render-demo.py`
and are not app screenshots or evaluation evidence. To regenerate those
illustrations, use Python 3 with Pillow:

```sh
python scripts/render-demo.py
```

The renderer accepts `--font-dir` for a directory containing DejaVu Sans and
DejaVu Sans Mono fonts; it also finds standard Windows and Linux fonts. Image
generation dependencies are only needed to edit the demo assets.
