# Crash-Safe Renames Implementation Plan

## Objective

Implement the approved crash-safe rename transaction design in
`docs/superpowers/specs/2026-09-30-crash-safe-renames-design.md`. The result must
never overwrite a path, must roll caught failures back, must recover an
interrupted transaction before accepting new work, and must leave the directory
unchanged when recovery inspection finds any conflict.

The repository remains dependency-free, uses ES modules and Node built-ins, and
runs tests with `node --test`.

## Proposed Module Boundaries

- `src/match.js`: input matching and exclusion of reserved internal names.
- `src/rename.js`: public planning, validation, recovery-first orchestration,
  and result/error types used by the CLI.
- `src/transaction.js`: journal publication, filesystem identity inspection,
  durable no-overwrite transitions, rollback, and recovery.
- `src/cli.js`: argument handling and stdout/stderr/exit-status presentation.
- `test/rename.test.js`: planning and high-level rename behavior.
- `test/transaction.test.js`: transaction state-machine and injected-failure
  tests.
- `test/cli.test.js`: child-process CLI behavior and crash-recovery coverage.

Filesystem operations in `transaction.js` should be accepted through a small
injected adapter. Production uses `node:fs`; tests wrap the adapter to fail at
specific link, sync, and unlink calls without changing production behavior.

# Crash-Safe, No-Overwrite Bulk Renames

## Purpose

`renamer` must apply a batch as one recoverable transaction. A caught error must
roll the batch back, and a killed process or machine failure must leave enough
durable state for the next invocation to restore the original names before it
accepts new work. Neither normal execution nor recovery may overwrite a file.

The directory can temporarily show an incomplete transaction after a crash.
The next invocation must recover it to the original state first and clearly
report the recovery. If recovery encounters any conflict, it must make no
further changes, report every exact conflict, exit unsuccessfully, and require
manual intervention.

## User-Visible Contract

An invocation performs these phases in order:

1. Detect and recover an existing transaction journal.
2. Refuse new work if recovery is unsafe or incomplete.
3. Plan the requested rename, excluding already completed output names.
4. Validate the entire plan and report every clash before changing files.
5. Execute the plan as a durable transaction.

Recovery actions and successful planned moves are written to stdout. Clashes,
recovery conflicts, and operational diagnostics are written to stderr. A
successful rename or clean no-op exits zero. A clash, unresolved recovery, or
operational failure exits nonzero.

A completed command is idempotent. For example, `photo-#.jpg` treats names
consisting of the literal prefix and suffix around `#`, with at least three
decimal digits in between, as completed outputs. Those files are excluded from
subsequent plans. A second identical run therefore does not renumber them.

## Components

### Planning

Planning keeps the existing lexical source ordering and numbering from one.
The first `#` in the replacement is the numeric placeholder, matching the
current replacement behavior. The generated number is padded to at least three
digits. Reserved `.renamer-` journal and staging names are never eligible input
files, even when the user's pattern would otherwise match them.

Before execution, validation collects all conflicts, including:

- an existing destination that is not the same recorded source file;
- duplicate destinations inside the plan;
- source, staging, or journal paths that cannot be used safely; and
- an already active transaction claimed by another invocation.

Validation does not mutate the directory. Any conflict prevents journal
publication and file movement.

### Transaction Journal

The canonical journal is `.renamer-transaction.json` in the target directory.
It contains a format version, transaction identifier, and one entry per file.
Each entry records its original name, unique staging name, destination name,
and original filesystem identity. Numeric identity fields that cannot be
represented safely as JSON numbers are encoded as decimal strings.

The complete journal is first written to a uniquely named temporary file. The
file is flushed before publication. Publication hard-links the temporary file
to the canonical journal name, providing an atomic no-clobber claim. The
directory metadata is then flushed. File movement cannot start before this
completes. A competing invocation that loses the claim removes only its own
unpublished temporary journal and exits without touching user files.

An unpublished temporary journal never authorizes recovery or file movement.
It can be reported as an orphan, but the canonical journal is the sole source
of transaction authority.

The canonical journal remains unchanged and authoritative throughout execution.
It is not removed until all intended destination entries and directory metadata
have been durably flushed. Journal removal is the commit boundary: if a crash
occurs before that removal is durable, the next invocation rolls the batch back.

### No-Overwrite File Transition

All source, staging, destination, and recovery moves stay within the target
directory and filesystem. A move is implemented as:

1. Create a hard link at the new name. Exclusive link creation fails if the
   name is occupied.
2. Flush directory metadata.
3. Remove the old name.
4. Flush directory metadata again.

This preserves the underlying regular file, avoids copy-time disk expansion,
and never uses rename behavior that can replace a destination on some
platforms. If the filesystem cannot provide the required hard-link and
durability operations, execution fails before user-file movement or rolls back
through the normal transaction mechanism.

The engine stages every source under its recorded unique name before creating
final destinations. If any staging or destination transition fails, it stops
forward execution and invokes rollback.

## Recovery and Rollback

Rollback after a caught error and recovery on a later invocation use the same
algorithm. The algorithm is repeatable so another interruption during recovery
can be handled by the next invocation.

Before changing anything, recovery scans the complete transaction read-only.
For each journal entry, the original data may be found at the source, staging,
or destination name, or briefly at more than one of those names when a process
stopped between link creation and old-link removal. Filesystem identity is used
to verify that every such path belongs to the recorded original file.

The complete transaction is recoverable only when:

- each original file exists at one or more of its recorded paths;
- every occupied recorded path has the expected identity;
- an occupied original source is the original file itself; and
- every extra link can be unambiguously attributed to that transaction entry.

Missing data, a changed identity, an unexpected occupant at any recorded path,
or any ambiguous state is a recovery conflict. Recovery collects every conflict
during the read-only scan. If at least one exists, it changes nothing further,
prints every conflicting path and reason, leaves the journal in place, and
requires manual intervention.

When the complete scan succeeds, recovery recreates each original source name
with the no-overwrite link operation and removes only verified transaction-owned
staging or destination links. An interruption can leave two verified links to
the same file; the next recovery safely recognizes that state. The journal is
removed and the directory flushed only after all original names are restored
and all transaction-owned extra links are removed.

Recovery always rolls a journaled batch back to its original names. New rename
planning never begins while an unresolved canonical journal exists.

## Failure and Concurrency Semantics

The design protects against expected filesystem errors, process termination,
machine failure, and concurrent `renamer` invocations. It does not silently
resolve interference by unrelated processes. Such interference becomes an
explicit conflict and blocks recovery rather than risking data loss.

Immediate rollback failure is reported with the failed operation. Its journal
remains authoritative so a future invocation can retry recovery. If that retry
finds an unexpected recreated source or any other conflicting path, it performs
no recovery mutations and requires manual intervention.

## Testing

Tests use isolated temporary directories and Node's built-in test runner. They
cover:

- successful multi-file renames;
- a completed command followed by a clean no-op rerun;
- multiple planning clashes reported together with no mutation;
- duplicate planned destinations;
- injected failure at each link, flush, and unlink transition;
- immediate rollback and rollback interrupted at every intermediate state;
- next-run recovery from every staged and partially committed state;
- repeated recovery after interruption;
- unexpected occupants, missing data, and changed identities producing a
  complete conflict report with zero recovery mutations;
- two processes attempting to publish a journal concurrently;
- orphan unpublished journals;
- unsupported hard-link or durability operations failing safely; and
- CLI stdout, stderr, and exit status behavior.

The tests compare directory entries and file contents before and after failed
operations. Conflict tests snapshot the directory before recovery and assert
that it remains byte-for-byte and name-for-name unchanged.

## Scope

The feature remains limited to regular files in one directory. It adds a
persistent transaction journal and automatic recovery, superseding the prior
decision not to keep rename state. It does not add a general undo command,
recursive traversal, dependency packages, or automatic conflict resolution.
