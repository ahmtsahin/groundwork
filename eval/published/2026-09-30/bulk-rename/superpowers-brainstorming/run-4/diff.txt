# Durable Rename Transactions Implementation Plan

## Goal

Replace sequential `renameSync` calls with a recoverable, no-overwrite
hard-link transaction. A run must validate all known conflicts before changing
source names, roll back runtime failures, recover interrupted work on the next
invocation, and refuse safely when recovery or required filesystem durability
cannot be established.

## Constraints

- ES modules and Node built-ins only.
- Tests run with `node --test`.
- User-facing results go to stdout; diagnostics go to stderr.
- No operation may overwrite an existing path.
- Unknown or externally changed files must not be deleted.
- A filesystem without hard-link and durable-journal support is rejected
  before any source name moves.

# Durable Rename Transactions

## Purpose

`renamer` must never knowingly overwrite a file or leave a partially applied
rename after a failure. Before starting a new rename, it must automatically
recover any interrupted transaction in the target directory. If external
changes prevent complete restoration, it must preserve those changes, report
every affected name, retain the recovery data, and refuse the new rename.

This design supersedes the README's version 1.1 decision not to keep a rename
journal. Crash and termination recovery now require a durable, directory-local
journal.

## User-visible behavior

- A complete plan is validated before any source name is removed.
- A destination that already exists is a conflict unless its step maps a file
  to itself. All conflicts are reported together and no files are changed.
- Two or more sources planned for the same destination are conflicts.
- Self-renames are harmless no-ops. If every step is a no-op, stdout says
  `no changes needed` and no transaction is created.
- A second process targeting a directory with a live renamer transaction
  refuses immediately and reports that another transaction is active.
- A runtime error triggers immediate rollback. When rollback succeeds, the
  diagnostic reports the original error and clearly states that no changes
  remained.
- `SIGINT` and `SIGTERM` initiate rollback where the platform permits.
  Uncatchable termination and machine or process crashes are recovered by the
  next invocation.
- An invocation that finds an interrupted transaction attempts recovery before
  planning new work. It starts the requested rename only after full recovery.
- An invocation that finds a durably committed transaction only finishes
  metadata cleanup; it does not roll back the completed rename.
- If recovery cannot restore an original name without overwriting an external
  file, or finds an unexpected file identity, it reports every affected name,
  retains the transaction data, and refuses new work.
- Rename and no-change reports go to stdout. Conflicts, transaction failures,
  recovery failures, and other diagnostics go to stderr and produce a nonzero
  exit status.

## Safety boundary

No program can guarantee restoration while unrelated software concurrently
changes the same names. `renamer` therefore never deletes or overwrites a path
whose recorded filesystem identity does not match. When external changes make
restoration unsafe, it reports incomplete recovery rather than claiming the
directory is unchanged.

The target filesystem must support hard links and the durable journal
operations described below. `renamer` verifies both capabilities with
disposable entries in the target directory before it removes any source name.
If either capability is unavailable, it refuses the plan without moving any
source.

## Architecture

The implementation has three responsibilities:

- `src/rename.js` builds plans, validates destinations, removes no-op steps,
  and coordinates transactions.
- `src/transaction.js` owns transaction acquisition, journal persistence,
  capability probes, hard-link execution, identity verification, commit,
  rollback, and interrupted-transaction recovery.
- `src/cli.js` recovers before starting new work and renders results and errors
  on the appropriate output stream.

Transaction metadata uses reserved names in the target directory. File
matching always excludes those names so no pattern can select a journal,
marker, or probe as an input.

## Preflight

Preflight runs after recovery and before transaction creation:

1. Remove exact `from === to` steps from the executable plan.
2. Validate that each source still exists and capture its filesystem identity.
3. Collect every existing destination and every destination assigned to more
   than one source. Report the full set if nonempty.
4. Create disposable entries in the target directory to verify exclusive hard
   linking, journal creation and flushing, and directory-entry durability.
5. Remove all probe entries. A probe cleanup failure is itself a refusal.

The journal is created with exclusive-create semantics only after these checks
succeed. Failures in this phase cannot leave source files renamed.

## Transaction ownership

The durable transaction header records a unique transaction identifier and
the owner's process identity. If a transaction exists and its recorded owner
is demonstrably alive, another invocation refuses immediately. If the owner is
not alive, the transaction is treated as interrupted and recovered. If owner
liveness cannot be established safely, the tool conservatively refuses rather
than risking interference with a live run.

Transaction ownership is directory-scoped: only one renamer transaction may
operate on a directory at a time.

## Journal format and durability

The journal is append-only. Its header contains the complete validated plan,
the identity of every source, and the transaction identifier. Subsequent
records describe intent and completion for each link, unlink, rollback, and
commit operation.

Before an operation that can change visible names, its intent record is
written and flushed. Completion is appended and flushed afterward. Required
directory entries are also flushed. The capability probe must demonstrate
these operations on the current platform and filesystem; otherwise execution
is refused.

Recovery does not assume that the last completion record survived. It
reconciles journal intent with the names and recorded file identities actually
present on disk. This makes a crash between an operation and its completion
record recoverable.

A durable commit record is the transaction's decision point. Before it, an
interrupted transaction is rolled back; after it, the rename is complete and
recovery only removes leftover transaction metadata. This prevents a crash
during post-commit cleanup from undoing a successful run.

## Applying a rename

Each executable step uses the following sequence:

1. Flush an intent-to-link record.
2. Create `to` with an exclusive hard link to `from`. Link creation fails if
   `to` appears during the run and cannot overwrite it.
3. Verify and flush link completion.
4. Flush an intent-to-remove-source record.
5. Verify that both names still identify the recorded file, then remove
   `from`.
6. Flush source-removal completion.

After all steps complete, the transaction is durably marked committed. Only
then is its metadata removed. Hard linking keeps file content and inode-backed
metadata intact and avoids copying large image files.

## Rollback and recovery

Rollback processes applied steps in reverse order. For each step it:

1. Reconciles the journal with the current identities of `from` and `to`.
2. If `from` is missing and `to` is the recorded file, recreates `from` using
   an exclusive hard link. It never overwrites an existing `from`.
3. After verifying that `from` is restored and both names identify the
   recorded file, removes the transaction-created `to`.
4. Flushes intent and completion records around each change.

If both names already represent the recorded file, recovery may safely remove
the transaction-created destination after identity verification. If a name is
occupied by another identity, a required recorded file is absent, or a durable
operation fails, recovery records and reports that affected name and leaves
the journal in place. It continues checking other steps so the final report
contains every known obstruction, but it performs only operations proven safe.

A fully restored transaction is marked recovered durably and its metadata is
removed. A partially restored transaction continues to block new renames and
can be retried by a later invocation after the external obstruction is
resolved.

## Error reporting

Errors are structured internally so the CLI can render a clear category,
summary, and list of affected names. Reports distinguish:

- preflight conflicts, followed by confirmation that no files were changed;
- unsupported hard-link or journal durability, followed by confirmation that
  no source was moved;
- execution failure with successful rollback, followed by confirmation that
  no changes remained;
- active transaction refusal; and
- incomplete recovery, listing every known obstruction and explicitly stating
  that the directory was not fully restored and no new rename was attempted.

The tool must not print `no changes needed` for a failed or blocked operation.

## Testing

Tests use isolated temporary directories and Node's built-in test runner. They
cover:

- ordinary successful renames;
- multiple existing destinations reported together with no changes;
- duplicate planned destinations;
- all-no-op and mixed no-op plans;
- exclusion of reserved metadata and probe names from matching;
- refusal by hard-link and durability capability probes before source changes;
- failures injected after destination linking and after source removal, with
  complete rollback;
- interrupted journals at every persisted state, followed by recovery;
- termination recovery behavior represented by persisted crash states;
- externally occupied original names and identity mismatches, proving that
  recovery neither overwrites nor deletes unfamiliar files;
- reporting of all recovery obstructions and preservation of the journal;
- refusal while the recorded owner is alive or liveness is indeterminate;
- retry and cleanup after a previously incomplete recovery;
- CLI exit status and stdout/stderr separation; and
- explicit success messages for rollback and no-op runs.

Tests inject filesystem failures through narrow internal operation interfaces
rather than relying on timing or platform-specific races. Production code
continues to use only ES modules and Node built-ins.
